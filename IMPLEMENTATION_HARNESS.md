# ChemAmaze AI/ML Implementation Harness

**Status:** Planning baseline — no application behavior changed by this document  
**Planning branch:** `plan/ai-ml-implementation-harness`  
**Baseline branch:** `main`  
**Project:** [dikshaforsure/ChemAmaze-cbse](https://github.com/dikshaforsure/ChemAmaze-cbse)

This file is the working contract for implementing ChemAmaze in small, reviewable phases. It is intended to be consulted before each coding phase, not treated as permission to implement all phases at once.

## 1. Product goal

Evolve the existing CBSE curriculum/game portal into **ChemAmaze AI**, a curriculum-grounded, adaptive science-learning system. The differentiating work should be measurable learning intelligence—not a generic chatbot attached to a website.

The target system will:
1. retain the existing subject/class/chapter/game navigation and preserve existing third-party game links;
2. add first-party, instrumented quizzes, because the application cannot assume it can read activity or answers inside cross-origin Wordwall iframes;
3. record privacy-minimizing answer events and maintain a concept-level learning state;
4. use an explainable knowledge-tracing model to estimate mastery;
5. select the next suitable learning activity using an explicit, testable policy;
6. offer optional curriculum-grounded question generation with source attribution, strict validation, and educator review;
7. evaluate model quality and learning outcomes against baselines and report limitations honestly.

**First end-to-end vertical slice:** one well-defined Science/chemistry topic, initially Class 7 Science — “Exploring Substances – Acidic, Basic, Neutral,” subject to verifying the exact curriculum/content license and instructor-approved scope. Do not build every grade or topic before this slice works.

## 2. Current repository baseline (observed)

The current repository is a small static web app with `index.html`, `index.css`, `script.js`, `logo.jpeg`, and `d-basf.png`. The reviewed `script.js` contains the subject/class/chapter catalogue, UI navigation, and Wordwall embed markup. The HTML presents home, subject, class, game-list, and game-player screens. There is no visible backend, database, package/dependency manifest, automated test suite, data pipeline, model-training code, or AI inference integration in the inspected tree. No README is present in the inspected tree.

Current behavior includes Mathematics and Science; classes 6, 7, and 8; and hard-coded game embeds. The app should be considered a **static game catalogue** at baseline—not described as an existing AI/ML system.

### Preserve by default
- Existing logo/image assets, branding, curriculum/game entries, links, and basic navigation.
- Existing game embeds as optional external activities.
- Existing deployment behavior while foundational work is added.
- All unrelated UI and wording unless a phase specifically requires a change.

### Known technical constraints
- Wordwall is served in cross-origin iframes. Do not rely on reading its DOM, answer events, scores, or identity unless an explicitly supported integration is verified.
- A question generated by an LLM must never be inserted into the page as trusted raw HTML. Render validated text/options using safe DOM APIs.
- Static JavaScript data is currently mixed with navigation logic. Restructure incrementally and add characterization checks before changing behavior.
- The current app uses no first-party quiz interaction model. Meaningful learner analytics require first-party questions and answer events.
- A generated answer is not a verified answer. Model output must be treated as untrusted candidate content.

## 3. Product and engineering principles

1. **One phase at a time.** Do not jump ahead, implement several phases in one change, or silently change the agreed architecture. At the end of a phase, report the diff, commands, tests, expected result, risks, and next phase.
2. **Minimize unrelated changes.** Keep existing navigation and embeds working. Refactors should have behavior checks and small diffs.
3. **Data before claims.** Synthetic data is useful for pipeline tests and learning the implementation; it is not evidence that real students learn better. Clearly label synthetic, public, and collected data.
4. **Baseline before complexity.** Compare ML to a transparent heuristic or simple statistical baseline. Prefer a simple interpretable model if it works adequately.
5. **No premature custom model training.** Start with an explicit knowledge-tracing model and evaluation harness. Train a misconception classifier only when an appropriate labeled dataset exists and passes a minimum-data review.
6. **Grounded educational content.** Use only materials the project is permitted to process. Track title, publisher/author when known, source URL or local reference, grade/topic, retrieval chunk, and usage rights. Do not scrape or republish restricted textbook content without permission.
7. **Human review for generated learning content.** Generated questions remain drafts until validation passes and a reviewer approves them. Persist provenance and model/prompt version.
8. **Provider independence.** Keep LLM and embedding providers behind interfaces/configuration. Do not put API keys in browser code or commit secrets.
9. **Privacy by design.** Use pseudonymous learner IDs, collect only the fields needed, restrict staff analytics, and avoid real student/minor data until consent, authorization, retention, and applicable institutional requirements are addressed. Do not put PII in logs.
10. **Measurable outcomes.** Maintain deterministic tests and versioned evaluation sets. Do not report invented performance numbers or claim educational impact without appropriate evidence.
11. **Accessibility and fallbacks.** Core quiz flows must work without AI availability; use keyboard-accessible controls, clear error states, and ordinary curated questions.
12. **No reinforcement learning in the first release.** We do not yet have a validated reward signal, safe exploration policy, or sufficient data. Use an inspectable recommendation policy first.

## 4. Target architecture (proposal)

Keep the current vanilla HTML/CSS/JavaScript frontend at first. Introduce modular boundaries without forcing a frontend rewrite. Add a separate Python API and ML/content services.

```text
Browser
  ├── Existing catalogue/navigation and Wordwall links
  ├── First-party quiz + mastery/revision views
  └── API client (no provider secrets)
          │ HTTPS / JSON
          ▼
Python API (FastAPI)
  ├── Curriculum / question-bank service
  ├── Learner session + attempt service
  ├── Knowledge tracing (BKT)
  ├── Recommendation policy
  ├── Misconception diagnostics
  └── Content retrieval / question-generation service
          │
          ├── PostgreSQL: curriculum, question versions, sessions,
          │               attempts, mastery state, review status
          ├── pgvector or a replaceable vector-index adapter:
          │               permitted source chunks and embeddings
          └── LLM/embedding provider interfaces
```

### Proposed stack
- **Frontend:** existing HTML/CSS/vanilla JS initially; use modules and safe DOM updates.
- **API:** Python 3.12+ and FastAPI, with Pydantic request/response schemas.
- **Persistence:** PostgreSQL, SQLAlchemy 2.x, and Alembic migrations.
- **Tests:** pytest for the backend/model; browser-based smoke or end-to-end tests for critical UI paths where practical; built-in Node tests for extracted pure JS logic if that avoids a front-end build-system migration.
- **ML/data:** Python, NumPy, pandas, scikit-learn for baselines and eligible classifiers.
- **Knowledge tracing:** an independently tested Bayesian Knowledge Tracing (BKT) implementation.
- **Retrieval/generation:** approved source material → parsing/chunking with metadata → embeddings/retrieval → structured candidate question generation → deterministic validation → human approval → published question bank.
- **Local development:** document reproducible commands; choose Docker Compose only if it simplifies the chosen Windows development workflow rather than adding unnecessary setup.
- **Vector storage:** decide during the retrieval phase based on selected PostgreSQL host and corpus size. Keep the interface replaceable; do not introduce a second database without demonstrated need.

Dependencies should be pinned and secrets managed through environment variables. Exact versions and hosting should be confirmed when the relevant phase begins; do not guess silently.

## 5. Data contracts (initial design, to be refined before migrations)

Use stable IDs rather than relying on display strings such as “Chapter 2.” Every question should be linked to one or more concept IDs and a source/provenance record where applicable.

| Entity | Purpose | Essential fields |
|---|---|---|
| Subject / grade / topic | Curriculum hierarchy | ID, name, grade, parent ID, syllabus/version |
| Concept | Unit whose mastery is estimated | ID, topic ID, name, description, prerequisite concept IDs |
| Question | Reusable, versioned assessment item | ID, concept IDs, stem, type, difficulty, status, source/version |
| Answer option | Safe structured content | ID, question ID, text, stable option key, correctness only server-side |
| Source document / chunk | Traceability for retrieval | source metadata, permitted-use note, chunk text/reference, checksum, embedding metadata |
| Learner session | Pseudonymous progress grouping | opaque ID/token hash, created/expiry/consent mode where applicable |
| Attempt | Raw learning event | learner session, question/version, selected option/answer, correctness, timestamp, attempt number, optional duration |
| Mastery state | Latest estimate per learner/concept | learner session, concept, probability, model/version, updated timestamp |
| Question candidate / review | Generated content lifecycle | candidate payload, source IDs, model/prompt version, validation results, reviewer/status |
| Recommendation event | Explainable activity choice | learner/concept, candidates considered, selected activity, policy/model version, reason |

These are logical entities, not a demand to create all tables at the start. Add tables only when their phase arrives. Avoid collecting names, school, exact location, free-text personal information, or other unnecessary identifiers.

### API direction (not a frozen contract yet)
- `GET /healthz`: service health, without secrets or sensitive configuration.
- `GET /api/v1/curriculum`: approved subjects, grades, topics, and concepts.
- `GET /api/v1/questions`: curated published questions filtered by concept/topic.
- `POST /api/v1/attempts`: validate and persist a first-party answer event.
- `GET /api/v1/me/mastery`: the current learner's mastery summary, after the session/access model is established.
- `GET /api/v1/me/recommendations`: next activity with a human-readable reason.
- Staff-only endpoints for review and aggregate insights will be specified alongside the relevant authorization design.

All schemas need explicit validation, stable error shapes, request limits, and versioning. Never return the answer key in the question-fetch response. Do not expose arbitrary learner records through a client-chosen ID.

## 6. ML and content design

### Knowledge tracing
Use BKT as the first principled model because it gives a probability of mastery per concept and makes its assumptions inspectable. The core parameters are:
- (P(L_0)): prior probability the learner already knows the concept;
- (P(T)): probability of learning between opportunities;
- (P(G)): probability of answering correctly despite not knowing the concept (guess);
- (P(S)): probability of an incorrect answer despite knowing it (slip).

Implement and unit-test both correct-answer and incorrect-answer updates, parameter bounds, and edge cases. Start with documented configurable parameters or fit aggregate parameters only when the available event data supports it. Do not treat the resulting probability as objective truth or a clinical/psychometric diagnosis.

### Recommendation policy
First make a deterministic policy: respect curriculum prerequisites, prefer concepts with lower estimated mastery or due revision, select a published and suitable question/activity, and record the reason. Compare this against fixed-order/random baselines. Do not start with reinforcement learning or claim causal improvement from offline scores.

### Misconception diagnostics
Start with an educator-reviewed misconception taxonomy and explicit mappings from known distractors/answer patterns to hypotheses. Label the output as a likely misconception, not a fact about the student. A classifier is a later, gated experiment requiring enough representative labeled examples, a held-out evaluation split, class-imbalance handling, and evidence that it beats a baseline. If that gate is not met, retain the rule-based approach.

### Curriculum-grounded generation
Treat generated content as candidate content. Store source identifiers and relevant evidence. Validate schema, option count, exactly one correct option for single-answer questions, non-empty explanations, grade/topic alignment, duplicate similarity, and answer consistency against the source. Automated checks can catch some failures, not guarantee truth; reviewer approval remains required. Separate retrieval quality evaluation from question-generation quality evaluation. Include a safe fallback to curated questions when the model, provider, or network fails.

### Evaluation rules
- Keep train/validation/test groups separated at the learner level when estimating generalization to unseen learners; for next-response prediction, use temporal ordering and prevent future attempts from leaking into features.
- Evaluate calibration and proper scoring metrics (e.g., log loss) as well as discrimination (e.g., AUC where appropriate).
- Retrieval: measure Recall@k or another suitable metric on a manually judged query set.
- Generation: measure groundedness, correctness, curriculum fit, duplication, and reviewer acceptance on a fixed test set.
- Misconceptions: use precision/recall/F1 and inspect class-wise results.
- Learning outcomes: compare pre/post or controlled conditions only with a defensible design and appropriate permissions. Model accuracy alone is not evidence of educational impact.
- Report dataset size, provenance, limitations, and confidence/uncertainty alongside metrics. Never fabricate results.

## 7. Thirty-phase implementation roadmap

Each phase should be completed, tested, reviewed, and summarized before the next phase begins. The phase can be split further if its acceptance gate proves too broad. Do not skip foundational gates merely to reach visible AI features sooner.

### Foundation and first-party learning data

#### Phase 01 — Baseline behavior inventory
**Work:** Map current screens, navigation transitions, game catalogue entries, external links, supported subjects/classes, assets, and known edge cases. Capture reproducible manual smoke-test steps.  
**Exit gate:** Existing navigation and game launch behavior are documented; baseline inventory matches the source files. No runtime behavior changes.

#### Phase 02 — Acceptance checks for existing behavior
**Work:** Add the smallest useful test/smoke harness around navigation and catalogue logic. Extract only the pure logic necessary for tests; avoid an unrelated framework rewrite.  
**Exit gate:** Tests or a repeatable smoke checklist cover home → subject → class → games → player → back/main, including empty catalogue behavior. Existing game URLs remain unchanged.

#### Phase 03 — Safe, incremental frontend modularization
**Work:** Separate catalogue data, screen/navigation behavior, and DOM rendering into clear files/modules, preserving the current design. Remove unsafe HTML interpolation for dynamic text where touched.  
**Exit gate:** The same screens and game links work; no visual redesign is bundled in; behavior checks pass.

#### Phase 04 — Structured curriculum/game catalogue
**Work:** Move the hard-coded catalogue into a validated JSON/data module with stable IDs for subject, grade, topic, and existing external activity. Preserve the original URL/embed mapping.  
**Exit gate:** A validator catches missing IDs, titles, grade/topic data, and invalid/missing embed URLs. All current catalogue entries are accounted for.

#### Phase 05 — Concept taxonomy and first-slice scope
**Work:** Define topic/concept IDs, prerequisites where justified, question types, difficulty labels, misconception tags, and source-provenance fields. Confirm the first chapter's content scope and permitted source material.  
**Exit gate:** A reviewed small concept map and content contract exist; no unsupported syllabus claims or unlicensed textbook corpus is introduced.

#### Phase 06 — Python API scaffold
**Work:** Add a separate Python service with FastAPI, configuration handling, dependency management, structured logs, request validation conventions, and a health endpoint.  
**Exit gate:** A clean environment can start the service using documented Windows-compatible commands; health and configuration tests pass; no secret is committed.

#### Phase 07 — Persistence and migrations
**Work:** Add PostgreSQL integration with SQLAlchemy and Alembic. Configure test settings separately from local/deployment settings.  
**Exit gate:** Migrations can create the initial schema from an empty database; rollback/rebuild instructions and connection-failure handling are documented.

#### Phase 08 — Versioned question bank and seed content
**Work:** Define server-side question/option schemas and seed a small, reviewed set for the first-slice concepts. Keep correctness keys server-side and attach concept/source metadata.  
**Exit gate:** Seed validation catches malformed questions and the question bank can be rebuilt reproducibly.

#### Phase 09 — Curriculum and question APIs
**Work:** Implement versioned read APIs for curriculum and published questions, filters by topic/concept, pagination where needed, response schemas, and consistent errors.  
**Exit gate:** API tests confirm only published questions are returned and answer keys never leak to the browser.

#### Phase 10 — First-party quiz experience
**Work:** Add a native quiz flow that uses the new APIs, provides immediate feedback from the server-verified answer, and supports a curated fallback when the API is unavailable. Preserve existing Wordwall launch options.  
**Exit gate:** A learner can complete a first-party quiz on desktop and mobile; keyboard operation and error/empty states work; existing navigation is still functional.

#### Phase 11 — Pseudonymous learner session
**Work:** Define a minimal session model to group progress without collecting unnecessary identity fields. Decide cookie/token handling, expiry, revocation, and local-development behavior.  
**Exit gate:** Session ownership is enforced by the backend; clients cannot read another learner's progress by changing an ID; logs contain no session token or personal data. Real school/minor deployments remain blocked until required approvals are in place.

#### Phase 12 — Reliable attempt-event recording
**Work:** Persist each answer attempt with question version, server-derived correctness, timestamp, concept mapping, attempt count, and carefully bounded optional duration. Handle retries/idempotency.  
**Exit gate:** Correct and incorrect attempts are reproducible from stored events; duplicate submissions do not corrupt progress; data integrity constraints and tests pass.

### ML foundations and adaptation

#### Phase 13 — Data quality, synthetic simulator, and exploratory analysis
**Work:** Build an explicitly synthetic event generator for pipeline smoke tests and an analysis script for real, permitted data when available. Document distributions, missing values, and label meaning.  
**Exit gate:** Synthetic data is labeled unmistakably; data-quality checks run; no synthetic metric is presented as real-world performance.

#### Phase 14 — Baselines and evaluation protocol
**Work:** Define prediction targets, baselines, data splitting rules, metrics, evaluation scripts, random seeds, and report format before tuning the model.  
**Exit gate:** A reproducible baseline can run end-to-end; there is no temporal or learner leakage; metric choice and limitations are documented.

#### Phase 15 — Bayesian Knowledge Tracing engine
**Work:** Implement BKT as a pure, independently tested module. Make parameters configurable, enforce valid ranges, handle missing/invalid answers, and produce an auditable mastery update.  
**Exit gate:** Formula-level unit tests cover correct/incorrect updates and boundary cases; output probabilities stay in [0, 1]; tests do not require a database or LLM.

#### Phase 16 — Mastery state and API
**Work:** Persist the latest learner/concept state with a model version and update it transactionally from accepted attempts. Provide a learner-scoped mastery endpoint.  
**Exit gate:** Replaying a known attempt sequence yields expected mastery states; updates are consistent under duplicate/retry handling; one learner cannot access another's state.

#### Phase 17 — Explainable recommendation baseline
**Work:** Implement a deterministic activity-selection policy using published activities, prerequisites, mastery estimates, and revision priorities. Log candidate set, selection, and reason.  
**Exit gate:** Given the same state and catalogue, recommendations are deterministic and explainable; the system has a fallback if there are no eligible questions.

#### Phase 18 — Misconception taxonomy and rules
**Work:** Define a small educator-reviewed taxonomy for the first slice and map meaningful distractors/answer sequences to tentative diagnostic labels.  
**Exit gate:** Rule behavior is covered by labeled examples; the interface describes results as likely patterns, not certain conclusions about a learner.

#### Phase 19 — Gate review for learned misconception classification
**Work:** Audit the volume, representativeness, permissions, and annotation quality of available labels. If data is adequate, build a simple classifier and compare it with rule/majority baselines; otherwise document why rules remain.  
**Exit gate:** The team records an evidence-based go/no-go decision. No classifier is shipped merely to claim “ML”; if implemented, held-out metrics and class-wise errors are reported.

### Grounded generative AI

#### Phase 20 — Permitted source ingestion and provenance
**Work:** Add a repeatable pipeline for approved documents/materials, with parsing, checksums, versioning, metadata, and explicit permitted-use tracking.  
**Exit gate:** Every indexed passage can be traced to its source and version; unsupported formats and permission-unknown content are rejected or held out.

#### Phase 21 — Retrieval and retrieval evaluation
**Work:** Chunk content with grade/topic/concept metadata, generate embeddings behind an adapter, retrieve relevant passages, and implement a manually judged retrieval set.  
**Exit gate:** Recall@k or an appropriate retrieval metric is reported on the fixed set; grade/topic filtering works; the storage choice and costs are documented.

#### Phase 22 — Structured question-generation adapter
**Work:** Add a provider-agnostic LLM interface and strict structured output schema for candidate questions, answer options, explanations, source IDs, and model/prompt version.  
**Exit gate:** Provider failure, timeout, malformed JSON, missing fields, and rate limits produce controlled failures; keys are server-side; generation does not auto-publish content.

#### Phase 23 — Candidate validation and grounding checks
**Work:** Add deterministic validators for schema, exactly one correct option for single-answer items, allowed concepts, option duplication, supported evidence, near-duplicates, and basic answer-key consistency. Record every validation result.  
**Exit gate:** Adversarial/invalid samples are rejected; source evidence is attached; documentation states what the automated checks cannot guarantee.

#### Phase 24 — Educator review and publishing workflow
**Work:** Add draft → validated → approved/rejected/published states, a reviewer interface or controlled internal workflow, audit history, and immutable question versions.  
**Exit gate:** Only authorized reviewers can publish; rejected drafts are not served; published questions preserve source and review provenance.

#### Phase 25 — Connect generation to the learning loop
**Work:** Allow the approved generated questions to enter the same question bank and recommendation path as curated questions, with per-concept limits and a curated fallback.  
**Exit gate:** No unreviewed generated item reaches learners; bad provider responses do not break quizzes; question versions are trackable in attempts.

### Feedback, evaluation, and readiness

#### Phase 26 — Learner mastery and revision view
**Work:** Show concept mastery estimates, attempted questions, recommended revision, and plain-language explanations for recommendations. Communicate uncertainty and avoid presenting estimates as definitive grades.  
**Exit gate:** The view uses backend data, explains stale/missing data, and passes privacy, keyboard, and responsive checks.

#### Phase 27 — Educator aggregate insights
**Work:** Build a limited view of aggregate concept difficulty, frequent distractors, and content-review status with access controls and minimum-group safeguards.  
**Exit gate:** Staff authorization is enforced; data is aggregated to reduce exposure of individual students; small-group disclosure risks are addressed before any deployment.

#### Phase 28 — Offline evaluation and learning-outcome pilot plan
**Work:** Compare BKT predictions and recommendation policies with baselines; evaluate retrieval and generated questions separately. Define a feasible, permissioned pre/post or comparison study before making educational-impact claims.  
**Exit gate:** Reproducible reports include data provenance, sample sizes, metrics, uncertainty, error analysis, and limitations. No fabricated or unsupported improvement claims.

#### Phase 29 — Security, reliability, accessibility, and deployment hardening
**Work:** Review authentication/session boundaries, authorization, input validation, safe rendering, API rate limits, dependency/security scanning, secret handling, backup/recovery, CORS, timeouts, logging, and accessibility. Add production deployment only after the selected host is tested.  
**Exit gate:** A documented checklist passes; secrets and personal data are absent from logs; failures have safe fallbacks; local setup and deployment instructions are repeatable.

#### Phase 30 — Final documentation and demonstrable evidence
**Work:** Document the architecture, data flow, model assumptions, endpoint contracts, data dictionary, setup, tests, evaluation, limitations, attribution (fellowship work vs later extension), and a concise demo script. Record final metrics only from actual runs.  
**Exit gate:** A new developer can run the system and reproduce tests/evaluation; the demo distinguishes existing platform features, new implementation, and future work; resume claims are traceable to code and evidence.

## 8. Phase execution contract

Before coding a phase:
1. Re-read this harness and inspect relevant current files/branch status.
2. State the exact phase goal, in-scope files, out-of-scope areas, assumptions, and acceptance checks.
3. Confirm prerequisites from earlier phases are actually satisfied; if not, address the blocker before proceeding.
4. Make the smallest coherent implementation on the planning branch (or the agreed continuation branch) and never commit secrets or student data.

After coding a phase:
1. Run applicable automated tests and report commands/results truthfully. If a test cannot run, state why and provide a manual fallback.
2. Inspect the diff for accidental changes, removed catalogue items, changed game URLs, data leaks, and unrelated formatting/rewrite changes.
3. Explain the key design choices in normal engineering terms.
4. Describe the expected visible/API/data outcome and how to verify it locally.
5. List known limitations and the next phase's entry conditions.
6. Stop and wait for review before starting the next phase.

## 9. Current decisions vs open decisions

### Decisions for the initial plan
- Preserve the static app as the starting UI; do not rewrite it in React/Next.js just because the project gains a backend.
- Keep existing external games, but do not treat iframe activity as measurable first-party learning data.
- Build one first-party chapter slice end-to-end before broadening curriculum coverage.
- Use FastAPI/PostgreSQL and an interpretable BKT baseline unless a concrete feasibility blocker appears.
- Keep generated content as reviewed drafts; never auto-publish LLM output.
- Treat real student deployment as a separate privacy/authorization milestone, not an automatic consequence of a working prototype.

### Resolve at the phase where evidence is available
- Final Python/package/Node versions and local environment orchestration.
- Specific PostgreSQL hosting and vector index choice.
- Approved curriculum source set and permitted-use constraints.
- Embedding model and LLM provider, including latency/cost limits.
- Minimum data/label thresholds before classifier work.
- Session mechanism and staff authentication for the actual deployment target.
- Whether a real-world learning study is feasible and permitted.

## 10. Definition of done for the overall project

ChemAmaze AI is ready to present as an AI/ML project only when the repository contains:
- a working first-party learning loop;
- traceable curriculum/question data and first-party answer events;
- a tested mastery model and explicit recommendation policy;
- baseline comparisons and reproducible evaluation;
- a grounded question-generation pipeline with a validation/review workflow (if that scope is completed);
- meaningful tests, setup instructions, architecture diagrams, and documented limitations;
- a clear distinction between fellowship contributions and post-fellowship extensions.

A running chatbot, an API integration by itself, synthetic-data-only model metrics, or a polished dashboard without validated underlying logic does **not** satisfy this definition of done.
